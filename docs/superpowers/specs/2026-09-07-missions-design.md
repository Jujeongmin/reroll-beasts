# 일일 미션 — 설계

매일 세 가지 과제를 준다. 다 하면 **시즌 패스 경험치**를 받는다.

`2026-09-03-home-lobby-design.md` §9 가 남겨 둔 마지막 칸이다. 패스·코스메틱·
결제는 다 섰는데, **패스를 올릴 이유가 판을 도는 것뿐**이다. 미션은 그 사이에
"오늘 이걸 하면 한 단계 더" 라는 짧은 목표를 끼운다.

## 1. 왜 지금 이걸 하나

지금 패스 경험치는 판 하나가 끝날 때 순위로만 오른다(`xpForRank`). 그래서

- 하루에 한 판만 하는 사람과 다섯 판 하는 사람의 차이가 **순위밖에 없다**.
  못하는 사람은 아무리 자주 들어와도 트랙이 거의 안 움직인다
- 오늘 들어올 이유가 없다. 판은 언제 해도 같은 값이라, 내일 해도 똑같다

미션은 둘 다 건드린다. **1위가 아니어도 오르는 경로**를 주고, **오늘 안에**
라는 시한을 붙인다. 새 재화를 만들지 않는다 — 패스라는 이미 있는 통에 넣는다.

## 2. 범위

**포함**

- 매일 3개. UTC 자정에 새로 갈린다
- 보상은 **패스 경험치만**. 젬·아바타를 직접 주지 않는다
- 과제는 두 갈래: **판 결과**(순위·모드·판수)와 **판 내용**(3성·시너지·아이템)
- 진행은 **판이 끝날 때** 서버가 센다. 라운드마다가 아니다
- 수령은 **버튼**. 다 찬 미션만 눌린다
- 홈에 미션 카드. 3줄 · 진행 막대 · [받기]

**제외**

- 주간 미션 · 시즌 미션. 만료 시각이 둘이면 저장도 둘이 된다
- 미션 새로고침(리롤). 3개가 매일 갈리는데 그것마저 바꿀 이유가 아직 없다
- 미수령 보상 이월. §6.3
- 미션으로 젬 주기. 젬은 파는 물건이라, 미션이 젬을 흘리면 상점이 흔들린다

## 3. 왜 이 모양인가 — 목록을 저장하지 않는다

**오늘의 3개는 저장하지 않는다.** 날짜와 계정으로 **다시 계산한다**.

```js
missionsFor(dayKey, account, data) // → [{ id, kind, target, xp, text }, ×3]
```

저장하면 "목록이 없으면 만들어 준다" 는 분기가 생기고, 그 분기가 곧 **목록이
두 벌**이 되는 자리다(서버가 만든 목록과 클라가 그린 목록). 서버와 클라가 같은
순수 함수를 돌리면 두 쪽이 다른 답을 낼 수 없다 — 이 저장소가 전투·LP·패스에서
계속 쓰는 방식 그대로다.

추첨은 `createRng(hash(dayKey + account))` 로 돌린다. 계정을 섞는 이유: 전원이
같은 3개를 받으면 "오늘은 랭크 미션뿐이라 할 게 없다" 가 모두에게 동시에
일어난다.

저장하는 것은 **진행도와 수령 여부뿐**이다.

## 4. 데이터 — `game/public/data/missions.json`

```json
{
  "perDay": 3,
  "missions": [
    { "id": "play_2",      "kind": "games",       "target": 2, "xp": 30,
      "text": "판 2번 끝내기" },
    { "id": "ranked_1",    "kind": "rankedGames", "target": 1, "xp": 30,
      "text": "랭크 판 1번" },
    { "id": "top4",        "kind": "top4",        "target": 1, "xp": 35,
      "text": "4위 안에 들기" },
    { "id": "win_1",       "kind": "firstPlace",  "target": 1, "xp": 50,
      "text": "1위 하기" },
    { "id": "three_star",  "kind": "threeStar",   "target": 1, "xp": 40,
      "text": "3성 유닛 만들기" },
    { "id": "trait_3",     "kind": "traitStep",   "target": 3, "xp": 35,
      "text": "시너지 하나를 3단계까지 올리기" },
    { "id": "items_3",     "kind": "itemsWorn",   "target": 3, "xp": 30,
      "text": "아이템 3개 장착하기" },
    { "id": "board_full",  "kind": "boardFull",   "target": 1, "xp": 25,
      "text": "레벨만큼 판을 꽉 채우기" },
    { "id": "round_wins",  "kind": "roundWins",   "target": 3, "xp": 35,
      "text": "한 판에서 라운드 3승" }
  ]
}
```

값의 근거: 패스는 한 단계에 100 경험치다(`pass.json`). 하루 3개를 다 하면
90~120 — **하루에 대략 한 단계**다. 판으로 버는 것(1위 100, 8위 26)과 비슷한
크기라야 미션이 판을 대체하지도, 장식이 되지도 않는다.

### 종류(kind)가 곧 판정 함수다

| kind | 무엇을 세나 | 어디서 나오나 |
|---|---|---|
| `games` | 끝낸 판 수 | 판 하나당 +1 |
| `rankedGames` | 랭크 판 수 | 랭크 방이면 +1 |
| `top4` | 4위 안 | `rank <= 4` 면 +1 |
| `firstPlace` | 1위 | `rank === 1` 이면 +1 |
| `threeStar` | 3성 유닛 | 마지막 판에 3성이 있으면 +1 |
| `traitStep` | 시너지 최고 단계 | 마지막 판의 최고 단계 (누적 아님, 최댓값) |
| `itemsWorn` | 장착한 아이템 수 | 마지막 판에 낀 아이템 총수 (최댓값) |
| `boardFull` | 꽉 찬 판 | 판에 선 수 ≥ 레벨이면 +1 |
| `roundWins` | 라운드 승수 | 그 판에서 이긴 라운드 수 (최댓값) |

**두 가지 셈법이 있다.** 판 수처럼 쌓이는 것(+1)과, 3성·시너지처럼 **한 판
안에서 얼마나 갔나**를 보는 것(최댓값). 뒤엣것을 더하기로 세면 "시너지 3단계"
가 1단계 세 판으로 채워진다 — 그건 다른 과제다.

## 5. 규칙 — `sim/missions.js`

전부 순수 함수다. 서버가 세고, 화면이 같은 함수로 그린다.

```js
/** UTC 날짜 도장. 'YYYY-MM-DD'. */
dayKeyOf(now)

/** 오늘의 3개. 저장하지 않고 다시 계산한다. */
missionsFor(dayKey, account, data)

/** 날짜가 갈렸으면 판을 새로 깐다. 같으면 그대로. */
rollMissions(prev, dayKey)   // → { day, progress: [0,0,0], claimed: [f,f,f] }

/** 판 하나를 반영한 새 상태. */
advanceMissions(prev, ctx, data)

/** 다 찬 미션을 받는다. → { state, xp } — xp 0 이면 못 받은 것이다. */
claimMission(prev, index, { dayKey, account }, data)
```

`ctx` 는 판 하나가 남긴 사실이다. **서버가 이미 쥐고 있는 값만 쓴다.**

```js
{
  account, dayKey,
  rank,            // 이 판의 최종 순위
  ranked,          // 랭크 방이었나
  board,           // 그 좌석의 마지막 배치 (정찰로 올라온 그 값)
  level,           // 그 좌석의 레벨
  roundWins,       // 그 판에서 이긴 라운드 수
}
```

`roundWins` 는 지금 없다. `sim/lobbyRound.js` 의 `resolveRound` 가 좌석마다
`seat.wins` 를 센다(연승 `streak` 을 세는 그 자리에서 한 줄). 승수는 순위로는
안 나온다 — 4위로 끝나도 라운드는 다섯 번 이겼을 수 있다.

`threeStar` · `traitStep` · `itemsWorn` · `boardFull` 은 `board` 에서 나온다.
시너지는 `activeTraits(board, data.traits)` 를 그대로 부른다 — 화면이 시너지
막대를 그릴 때 쓰는 그 함수다. 여기서 다시 세면 두 답이 갈린다.

## 6. 저장

### 6.1 모양

`profile.missions` 하나. 프로필은 이미 서버가 판 끝에 쓰는 문서다.

```json
{ "day": "2026-09-07", "progress": [2, 0, 1], "claimed": [true, false, false] }
```

세 칸은 `missionsFor` 가 낸 **순서 그대로**다. id 를 키로 쓰지 않는 이유:
같은 날 같은 계정이면 목록이 항상 같은 순서로 나오므로 자리로 충분하고,
id 를 적으면 표를 고칠 때 저장된 id 가 사라져 "모르는 미션의 진행도" 가 남는다.

### 6.2 날짜가 갈리면

읽는 순간 `rollMissions` 가 판을 새로 깐다. 서버에 타이머가 없다(자정에 깨어날
수단이 없다) — 그래서 **누가 찾아올 때** 판정한다. 마감·매칭이 쓰는 방식과 같다.

### 6.3 미수령은 사라진다

날짜가 갈리면 다 찬 미션도 함께 지워진다. "오늘 것" 이라 그렇고, 안 그러면
밀린 보상이 쌓여 **매일 들어올 이유가 없어진다** — 일주일 뒤에 몰아 받으면
된다. 그 대신 화면이 미리 말한다: 카드에 남은 시간을 적는다.

## 7. 서버

두 자리만 건드린다.

**판 끝** — `resolveRound` 안, `applyMatchResult` 옆. 순위가 박히는 그 자리에
판 결과와 마지막 보드가 다 있다. 프로필을 쓰는 같은 계정 락 안에서 함께 쓴다.

```ts
const next = applyMatchResult(prev, rank, DATA, { ranked, matchId })
next.missions = advanceMissions(prev?.missions, ctx, DATA)
```

같은 판을 두 번 세지 않는 규칙(`countedMatch`)이 미션에도 그대로 걸린다 —
프로필 하나를 통째로 건너뛰기 때문이다.

**수령** — 새 함수 `claimMission(index)`.

```ts
async claimMission(index: number): Promise<any>
```

계정 락 안에서 프로필을 다시 읽고, `claimMission` 순수 함수가 "정말 다 찼나 ·
이미 받았나" 를 판정한다. **화면에서만 막으면 잠금은 장식이다** — 조작된 호출
하나로 안 한 미션의 경험치가 들어온다.

경험치는 패스에 얹는다. 지금 `advancePass` 는 순위를 받아 계산하므로 그대로는
못 쓴다 — `sim/pass.js` 에 **경험치를 직접 더하는** 함수를 낸다.

```js
addPassXp(pass, xp, data)  // → { xp, level, premium, earned }
advancePass(prev, rank, data, opts)  // 이제 addPassXp 를 부른다
```

단계가 오르면 젬도 같이 나온다(`gemsBetween`). 그 셈을 두 곳에 적으면 미션으로
오른 단계만 젬을 안 주는 일이 생긴다 — 한 함수로 모은다.

## 8. 화면

홈 좌측, **시즌 패스 카드 바로 위**. 미션 경험치가 그 게이지로 들어가므로 둘이
붙어 있어야 인과가 보인다.

```
┌──────────────┐
│ 오늘의 미션   │  남은 시간 6:12
│ 판 2번 끝내기 │  ▓▓▓▓▓▓░░░░ 1/2
│ 3성 만들기    │  ▓▓▓▓▓▓▓▓▓▓ [받기]
│ 랭크 판 1번   │  ░░░░░░░░░░ 0/1   ← 받음 표시는 회색으로 남는다
└──────────────┘
```

- 다 찬 줄에만 [받기]. 받은 줄은 **사라지지 않고** 회색으로 남는다 — 줄이
  사라지면 오늘 뭘 했는지가 화면에서 지워진다
- 서버가 없으면 카드가 안 뜬다. 미션은 계정에 쌓이는 값이라 로컬로 흉내 낼 수
  없다(홈의 다른 서버 의존 칸과 같은 규칙)
- 진행도는 홈에 들어올 때 받은 프로필에서 그대로 읽는다. 판이 끝나야 바뀌는데
  그때는 홈에 없다 — 별도 폴링이 없다

## 9. 검증

| 무엇 | 어디서 |
|---|---|
| 추첨이 같은 날·같은 계정이면 같은 3개 · 다른 계정이면 갈린다 | vitest |
| 종류별 셈법(더하기 vs 최댓값) | vitest |
| 날짜가 갈리면 진행·수령이 초기화된다 | vitest |
| 안 찬 미션·이미 받은 미션은 수령이 거절된다 | vitest |
| 판 끝에 진행이 오른다 · 같은 판을 두 번 안 센다 | 서버 테스트 |
| 수령이 패스 경험치를 올린다 · 단계가 오르면 젬도 | 서버 테스트 |
| 카드 배치·남은 시간·받기 버튼 | 브라우저 |

불변식(`tools/validate.mjs`)에 세 줄 추가한다.

- 미션 id 가 겹치지 않는다
- 모든 미션의 `target` 이 1 이상 정수, `xp` 가 양수
- 모든 `kind` 가 `sim/missions.js` 가 아는 것 — 모르는 종류는 **조용히 0 점**이
  된다. 화면에는 뜨는데 영원히 안 차는 미션이 그것이다

`npm run check` 는 계속 초록이어야 한다.
